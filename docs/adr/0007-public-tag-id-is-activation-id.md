# ADR 0007: Public Tag ID Is the Activation ID

**Status:** Accepted
**Date:** 2026-07-28
**Scope:** Phase-one product invariant

## Context

Every ReturnTag physical product displays one public six-character Tag ID and
an HTTPS QR URL containing that ID. The same identifier is required for QR
routing, manual entry, first activation, finder scans, and support lookup.

Because the identifier is visible before sale, it cannot be treated as a
secret. Introducing a second Claim ID, hidden activation secret, package code,
order mapping, or logistics mapping would contradict the frozen phase-one
product model and create additional manufacturing, support, privacy, and
rollback complexity.

This decision was already frozen in the PRD and repository instructions. This
ADR records the long-lived tradeoff under the next available ADR number; ADR
0001 is already assigned to feature-flag runtime semantics.

## Decision

Each physical Tag has exactly one canonical public Tag ID:

```text
Length:   6 characters
Alphabet: 23456789ABCDEFGHJKLMNPQRSTUVWXYZ
```

The public Tag ID is also the first-activation ID. The same value is used for:

```text
QR routing
manual entry
first activation
finder scans
support lookup
```

There is no separate Claim ID, claim secret, hidden package activation code,
pack claim flow, or secondary activation credential.

Tag IDs are generated by production Batch with a cryptographically secure
random source. Database uniqueness is authoritative, collisions retry safely,
and every generated, exported, voided, suspended, or retired ID is permanently
non-reusable.

WooCommerce orders, Amazon orders, order items, shipments, packages, tracking
numbers, and logistics records are never mapped to a Tag ID.

Because the public ID is not a secret, first activation requires compensating
controls:

- new Batches default to activation disabled;
- only released and enabled Batches may activate unregistered Tags;
- activation requires verified email OTP;
- activation attempts are rate-limited by privacy-safe risk signals;
- ownership is assigned through an atomic conditional database write;
- conflicts reveal no current Owner information;
- exports are access-controlled, immutable, checksummed, and audited;
- leaked Batches can suspend new activation without silently disabling
  already active Owners;
- ownership disputes require an approved administrative review flow.

## Consequences

- Manufacturing prints one stable human-readable ID and one QR URL per Tag.
- Activation cannot rely on secrecy of the printed identifier.
- Email OTP proves control of an email address, not possession or purchase of a
  specific Tag; residual pre-claim risk remains and is handled by the approved
  compensating controls.
- Orders and logistics cannot be used as automatic Tag ownership evidence.
- Code rollback, incident response, test cleanup, and Batch failure handling
  must never delete or recycle a generated ID.
- Any proposal for a second activation credential or an order/Tag mapping
  requires an explicit PRD change and a superseding ADR.

## Rejected alternatives

- **Separate Claim ID or hidden activation code:** contradicts the frozen
  one-ID product model and adds a second manufacturing secret.
- **Order or shipment allocation:** violates channel independence and prevents
  gift recipients from activating with their own verified identity.
- **Predictable Batch-derived IDs:** weakens enumeration resistance and
  collision safety.
- **Deleting failed or voided IDs for reuse:** breaks export immutability,
  auditability, and incident containment.

## Rollback

This ADR changes no code, Schema, Option, Hook, route, or stored data. Existing
Tag IDs and their anti-reuse guarantee remain authoritative. A documentation
rollback must not be interpreted as permission to add a Claim ID, map orders
to Tags, or reuse any generated identifier.
